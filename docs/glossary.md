## Контроллер (control node)

Машина или среда, из которой запускают Ansible. Контроллер читает playbook
и inventory, подготавливает задачи, подключается к целевым хостам и получает
результаты.

## Плейбук (playbook)

YAML-файл, описывающий один или несколько plays: к каким хостам применить
настройки и какие задачи выполнить.

## Стратегия (strategy)

Плагин Ansible, определяющий, как организовать выполнение задач на хостах.
Например, стандартная стратегия `linear` выполняет очередную задачу на хостах
текущей группы выполнения (batch), прежде чем переходить к следующей.
Стратегия координирует работу исполнителей, но не реализует логику
прикладного модуля.

## Целевой хост (managed node, target host)

Машина, на которой Ansible должен выполнить задачу.

## Become (повышение или смена привилегий)

Механизм Ansible для выполнения команды от имени другого пользователя.
`become: true` включает его; `become_user` задаёт пользователя, а
`become_method` — способ переключения. Обычно это переход к root через sudo,
но become не ограничивается sudo и не обязательно повышает привилегии.

## Sudo и sudo-права

`sudo` — программа, позволяющая выполнять разрешённые команды от имени
другого пользователя, часто root. «Sudo-права» — разрешения, заданные
политикой sudo, например в sudoers: какие команды, от чьего имени и
с каким требованием пароля можно запускать.

Это не отдельный вид прав доступа к файлам. Вход по SSH сам по себе не даёт
sudo-прав.

## SSH (Secure Shell)

Протокол защищённого удалённого доступа: позволяет аутентифицироваться
на сервере и выполнять команды через зашифрованное соединение. Ansible
использует SSH также для передачи кода модуля и получения результата.
SSH также поддерживает туннелирование: передачу соединений к заданному
сетевому порту через защищённый канал.

## Ansiballz

Механизм Ansible для подготовки и запуска Python-модулей. Контроллер собирает
модуль и необходимые зависимости из module_utils в ZIP, кодирует архив
в Base64 и включает его вместе с параметрами в Python-обёртку.
На целевом хосте обёртка восстанавливает архив и запускает модуль через
загрузчик. Модуль возвращает результат в JSON.

Ansiballz не является постоянно работающим агентом на сервере.
Сборка архива, передача и запуск — разные этапы выполнения модуля.

## Callback (плагин обработки событий)

Плагин Ansible, реагирующий на события выполнения: начало play или задачи,
успех, ошибку, пропуск и итоговую статистику. Например, stdout callback
форматирует вывод терминала с `ok`, `changed`, `failed` и `PLAY RECAP`.
Callback работает на контроллере и обрабатывает уведомления о выполнении,
а не реализует полезную логику модулей.

TaskQueueManager организует передачу событий callback-плагинам.
В контексте Ansible термин обозначает подсистему плагинов обработки событий;
в общем программировании callback — функция, переданная для последующего вызова.

## Inventory (инвентори)

Описание управляемых хостов, групп и связанных с ними переменных.
Бывает статическим (например, YAML-файл) или динамическим: хосты получает
inventory-плагин из внешнего источника. Один хост может входить в несколько групп.
Inventory задаёт, какие машины известны Ansible; поле `hosts` в play выбирает,
к каким из них применить задачи.

Имя хоста в inventory может быть псевдонимом: `ansible_host` задаёт адрес
подключения, а `ansible_user` — пользователя для подключения.

## Vars (переменные, «варсы»)

Именованные значения: строки, числа, логические значения, списки и словари.
Используются при подстановке аргументов, в условиях и шаблонах.
Например, `{{ http_port }}` подставляет значение переменной `http_port`.

Параметр запуска `-e http_port=8080` задаёт переменную, которую можно
использовать в аргументах задач. Выражение `{{ http_port | default(80) }}`
использует запасное значение, если переменная не определена.
Фильтр `default` и role defaults — разные механизмы задания значений по умолчанию.

### Область действия и приоритет

Область действия отвечает на вопрос «где доступно значение», приоритет —
«какое значение выбрано при совпадении имени». Это разные понятия.
Различают настройки уровня запуска, контекст play и значения, связанные
с хостом. Внутри play есть более узкие области: роль, block, task.
`group_vars` задаёт значения группе, `host_vars` — конкретному хосту.

### Уровни приоритета: от низкого к высокому

Ниже порядок из документации Ansible. Нижняя строка перекрывает верхнюю
при совпадении имени и применимости обеих настроек.
Первая строка включена для полноты исходного списка: обычные CLI-опции
сами по себе не являются переменными.

| № | Источник |
| --- | --- |
| 1 | Обычные CLI-опции, например `-u` |
| 2 | Role defaults: `roles/<role>/defaults/main.yml` |
| 3 | Переменные групп непосредственно в inventory |
| 4 | `group_vars/all` рядом с inventory |
| 5 | `group_vars/all` рядом с playbook |
| 6 | `group_vars/<group>` рядом с inventory |
| 7 | `group_vars/<group>` рядом с playbook |
| 8 | Переменные хоста непосредственно в inventory |
| 9 | `host_vars/<host>` рядом с inventory |
| 10 | `host_vars/<host>` рядом с playbook |
| 11 | Facts и кэшированные `set_fact` |
| 12 | `vars` уровня play |
| 13 | `vars_prompt` |
| 14 | `vars_files` |
| 15 | Role vars: `roles/<role>/vars/main.yml` |
| 16 | `vars` уровня block |
| 17 | `vars` уровня task |
| 18 | `include_vars` |
| 19 | `register` и текущие `set_fact` |
| 20 | Параметры role / `include_role` |
| 21 | Параметры include |
| 22 | Extra vars: `-e`, `--extra-vars` |

Источник: [Using variables — приоритеты](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_variables.html#understanding-variable-precedence).

### Термины источников переменных

- **Role defaults** — переопределяемые значения по умолчанию роли.
- **Role vars** — переменные роли с более высоким приоритетом.
- **Play vars / block vars / task vars** — переменные соответствующей области.
- **Facts** — сведения о хосте, например ОС и сетевые интерфейсы;
  обычно собираются модулем setup. Это не все переменные хоста вообще.
- **`register`** — сохранение результата задачи под именем переменной.
  Например, `register: task_result` сохраняет результат задачи в `task_result`.
- **`set_fact`** — назначение переменной, связанной с хостом, во время выполнения.
  При `cacheable: true` кэшированная копия в следующем запуске имеет приоритет facts,
  а значение текущего запуска — приоритет текущего set_fact.
- **`include_vars`** — загрузка переменных из файла или каталога задачей.
- **`vars_files`** — файлы переменных, указанные в play.
- **`vars_prompt`** — интерактивный запрос значения.
- **Extra vars** — явные переменные запуска, заданные через `-e` или `--extra-vars`.

Переменные подключения, например `ansible_user`, могут перекрывать обычные
CLI-опции и playbook keywords. Поэтому `-u deploy` и `-e ansible_user=deploy`
имеют разный приоритет. Конфигурация, переменные окружения, CLI-опции,
keywords и vars — разные категории настроек, а не одна лестница vars.
См. [общие правила приоритета](https://docs.ansible.com/projects/ansible/latest/reference_appendices/general_precedence.html).
